## 1. Objetivo
Adicionar reconexão automática com **exponential backoff** ao `WebSocketControlClient` (T-009b) e ao `BrowserWebSocketControlClient` (T-009c). Quando a conexão WebSocket cai inesperadamente (close sem ser por `close()` explícito do cliente), o cliente tenta reconectar com delay progressivo até um limite máximo de tentativas.

> **Derivação:** Decisão D3 de T-009b §6 cortou reconexão do M0 e moveu para follow-up. Esta task é esse follow-up. *(fonte: `tasks/T-009b.md` §6 D3)*

### Contratos exatos (derivados de T-009b + padrão exponential backoff)

```ts
// --- packages/client-sdk/src/WebSocketControlClient.ts (UPDATE) ---
// Adicionar ao export existente

export interface ReconnectOptions {
  /** Delay inicial entre tentativas (ms). Default: 1000. */
  initialDelayMs?: number;
  /** Fator de multiplicação do backoff. Default: 2. */
  backoffFactor?: number;
  /** Delay máximo entre tentativas (ms). Default: 30000. */
  maxDelayMs?: number;
  /** Número máximo de tentativas antes de desistir. Default: 10. 0 = infinito. */
  maxRetries?: number;
  /** Jitter máximo adicional (ms), aleatório 0..jitterMaxMs somado ao delay calculado. Default: 1000. */
  jitterMaxMs?: number;
}

/** Eventos emitidos pelo cliente (via callback ou EventEmitter). */
export interface ReconnectEvents {
  /** Disparado quando uma tentativa de reconexão vai começar. */
  onReconnecting?: (attempt: number, delayMs: number) => void;
  /** Disparado quando o número máximo de tentativas foi atingido sem sucesso. */
  onReconnectFailed?: (lastError: Error) => void;
}

// --- Construtor atualizado (WebSocketControlClient) ---
// constructor(url: string, token: string, reconnectOpts?: ReconnectOptions & ReconnectEvents)
// Nova overload aceita objeto de opções de reconexão.

// --- BrowserWebSocketControlClient (T-009c, mesmo padrão) ---
// constructor(url: string, token: string, reconnectOpts?: ReconnectOptions & ReconnectEvents)
```

**Comportamento da reconexão:**
1. A reconexão só dispara em **close inesperado** — se `close()` foi chamado pelo cliente, NÃO reconecta.
2. Delay da n-ésima tentativa (0-based): `min(initialDelay * backoffFactor^n + random(0, jitterMaxMs), maxDelayMs)`.
3. Se `maxRetries === 0`, tenta indefinidamente (respeitando `maxDelayMs`).
4. Se a conexão for estabelecida com sucesso, o contador de tentativas zera (próxima queda começa de `initialDelay`).
5. Durante a reconexão, mensagens recebidas do `ControlPort` (via `bind`) são **enfileiradas** e enviadas quando a conexão restabelecer.
6. Se o token expirou (servidor fecha com 1008), a reconexão NÃO é tentada — o erro é propagado via `onReconnectFailed`.

Casos de teste (unitários, em `reconnect.test.ts`):
1. `createBackoff({initialDelayMs: 100}).nextDelay()` retorna 100 (± jitter).
2. Após 3 tentativas com `backoffFactor: 2`, delay = 100 → ~200 → ~400.
3. `maxDelayMs: 500` — delay não ultrapassa 500 mesmo com muitas tentativas.
4. `reset()` zera o contador; próximo `nextDelay()` retorna delay inicial.
5. `maxRetries: 3` — `getAttempt()` retorna 0,1,2,3; na 4ª fica 3 (não avança).

Casos de teste (integração, em `WebSocketControlClient.test.ts`):
6. Cliente conecta, servidor fecha conexão → `onReconnecting` dispara com attempt=1, delay > 0.
7. Servidor aceita reconexão → `onReconnecting` para de disparar; `connect()` resolve.
8. Servidor rejeita consistentemente por `maxRetries` vezes → `onReconnectFailed` dispara com o último erro.
9. `close()` explícito do cliente → NÃO dispara reconexão.
10. Servidor fecha com 1008 (`missing_session_token`) → NÃO reconecta (token inválido não vai mudar).

### Pegadinhas conhecidas
- **Armadilha:** O `close` event do WebSocket dispara tanto para fechamento do servidor quanto para `ws.close()` do cliente. Usar uma flag `_userClosed = true` antes de chamar `ws.close()` para distinguir.
- **Armadilha:** Durante a reconexão, o `ControlPort.bind` já foi chamado. Comandos do Hub que chegam durante o período offline são perdidos (o Hub dá timeout após 5s). Enfileirar eventos do ControlPort só faz sentido para envio de telemetria, que está cortada (D2). Para V0, registrar warning e ignorar é aceitável.
