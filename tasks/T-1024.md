## 1. Objetivo
Evoluir o serviço de worktrees de **efêmero-por-task** (cria worktree no `start`, remove no `approve`) para um **pool de worktrees longevas** que mantêm `node_modules` quente entre tasks. Hoje cada task isolada paga um `pnpm install` novo (lento no Windows/ARM64 por causa da floresta de symlinks `.pnpm`). Com pool, o `pnpm install` roda **uma vez por slot** (na criação) e só repete se o `pnpm-lock.yaml` mudar; trocar de task é só um `git checkout` de branch no slot.

**Gatilho de adoção:** isto só compensa quando o Runner virar **concorrente** (vários workers ao mesmo tempo). Esta task **adiciona** o modo pool atrás de uma flag, **sem remover nem alterar** o caminho efêmero atual (que continua o default).

> **Derivação:** Contratos de pool derivados de `T-1012.md` (worktree.service.ts — `done`, merged). Comportamento de `ensureTaskWorktree`/`removeTaskWorktree`/`git worktree add`/`git checkout -B` observado no código merged de T-1012. *(fontes: `tasks/T-1012.md`, `apps/nexus-backend/src/services/worktree.service.ts` — este último pode não existir na worktree atual por causa do congelamento do Nexus; ver Seção 6 OPEN-1).*

### Contratos exatos (assinaturas TS fixadas — destino a definir pelo arquiteto)

```ts
// --- <caminho a definir pelo arquiteto (OPEN-1)>/worktree.service.ts (UPDATE) ---
// Adicionar (NÃO remover nem alterar as funções existentes):

export class NoWorktreeAvailableError extends Error {
  constructor(poolSize: number) {
    super(`Pool de worktrees esgotado (todos os ${poolSize} slots ocupados).`);
    this.name = 'NoWorktreeAvailableError';
  }
}

export interface PoolSlot {
  slot: string;            // 'slot-1' .. 'slot-N'
  path: string;            // <base>/pool/<slot>
  branch: string | null;   // 'task/<id>' quando ocupado, null quando livre
  lockfileHash: string | null; // sha256 do pnpm-lock.yaml na última provisão; null = nunca provisionado
}

export interface PoolOptions {
  rootDir?: string;                                        // default: NEXUS_ROOT_DIR ou process.cwd()
  baseDir?: string;                                        // default: NEXUS_WORKTREE_DIR ou <root>/../.nexus-worktrees
  poolSize?: number;                                       // default: NEXUS_WORKTREE_POOL_SIZE ou 2
  installer?: (slotPath: string) => Promise<void>;         // default: pnpm install --prefer-offline --frozen-lockfile (injetável p/ teste)
}

// Idempotente: cria <base>/pool/<slot-n> (git worktree add --detach) para n=1..poolSize
// e o registro <base>/pool/registry.json se não existirem. Retorna os slots.
export async function ensureWorktreePool(opts?: PoolOptions): Promise<PoolSlot[]>;

// Aloca um slot para a task `id`:
//  - se algum slot já tem branch === `task/<id>` → retorna esse (idempotente);
//  - senão pega o primeiro slot livre (branch === null); se nenhum → lança NoWorktreeAvailableError;
//  - no slot escolhido: `git checkout -B task/<id>` (cria/reseta a branch a partir do HEAD do slot);
//  - provisão: calcula sha256 do pnpm-lock.yaml do root; se slot.lockfileHash !== hash atual →
//    roda opts.installer(slotPath) e grava o novo hash; se igual → PULA (node_modules quente);
//  - persiste o registro. Retorna { branch, path, slot }.
export async function acquireWorktree(id: string, opts?: PoolOptions): Promise<{ branch: string; path: string; slot: string }>;

// Libera o slot da task `id`: `git checkout --detach` no slot, marca branch=null no registro.
// NÃO apaga o diretório nem o node_modules (mantém quente). No-op se id não estiver alocado.
export async function releaseWorktree(id: string, opts?: PoolOptions): Promise<void>;
```

Regras de implementação fixas:
- Base do pool: `path.join(baseDir, 'pool')`. Registro: `<base>/pool/registry.json`.
- `poolSize` resolve de `opts.poolSize ?? Number(process.env.NEXUS_WORKTREE_POOL_SIZE) || 2`.
- Hash do lockfile: `crypto.createHash('sha256').update(fs.readFileSync(path.join(root,'pnpm-lock.yaml'))).digest('hex')`.
- `installer` default:
  `(p) => execa('pnpm', ['install','--prefer-offline','--frozen-lockfile'], { cwd: p })`
  reutilizando o mesmo padrão `execa`/`execFile`-em-Promise usado por `git()` no código existente.
  Timeout generoso (≥ 600000ms).
- Reutilizar `getWorktreeList`/`branchExists` existentes; NÃO criar um segundo parser de worktree.

Casos de teste (numerados, em `worktree-pool.test.ts`):
1. `ensureWorktreePool({poolSize:2})` cria 2 worktrees em `<base>/pool/slot-1|2` + `registry.json`; idempotente ao rodar 2×.
2. `acquireWorktree('T-A')` → retorna slot livre, branch `task/T-A`, e chama o `installer` 1×.
3. `acquireWorktree('T-A')` de novo → mesmo slot (idempotente), `installer` NÃO é chamado de novo (hash do lockfile inalterado).
4. Com `poolSize:1`, `acquire('T-A')` ok e `acquire('T-B')` → lança `NoWorktreeAvailableError`.
5. `releaseWorktree('T-A')` → slot fica `branch:null`, diretório e `node_modules` fake permanecem; `installer` NÃO é chamado.
6. Após release, `acquire('T-B')` reusa o slot livre; como o lockfile não mudou, `installer` NÃO é chamado (quente).
7. Mudar o conteúdo de `pnpm-lock.yaml` e `acquire` de novo → `installer` É chamado (hash divergiu).

### Pegadinhas conhecidas
- `git checkout -B` em um slot exige que o slot NÃO tenha mudanças não-commitadas; como o pool só faz `--detach` no release, os slots ficam limpos.
- Uma branch `task/<id>` não pode estar em dois slots ao mesmo tempo. O registro é a fonte da verdade.
- `crypto`, `os`, `fs`, `path` são imports de node; não esquecer `import crypto from 'crypto'`.
