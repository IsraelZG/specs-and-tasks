# C-36 · Corrigir fallback WASM do Zen Engine no Windows ARM64

## 0. Ambiente de Execução Obrigatório

- **Repo de controle:** `C:\Dev2026\Docs` — lifecycle pelo `manage-task.mjs`; não fazer git.
- **Repo de código:** `C:\Dev2026\superapp`, em worktree `task/C-36`.
- **Runtime observado:** Node.js em `process.platform === "win32"` e `process.arch === "arm64"`.
- **Package manager:** `pnpm`.
- **Capacidade-alvo:** **sonnet** — mudança pequena, mas a resolução de binário opcional precisa ser
  comprovada no host ARM64, sem substituir o motor nativo por um mock.
- **Gate:** `pnpm gate @plataforma/estaleiro --profile full`.

## 1. Objetivo

Desbloquear o carregamento de `@gorules/zen-engine` no Windows ARM64 e, por consequência, o gate
pós-merge da EST-73. A C-29 introduziu em `apps/estaleiro/package.json` uma dependência opcional
específica de Windows x64; o pacote upstream não publica `win32-arm64-msvc`, e sua resolução tenta
carregá-la no host ARM64 antes de os testes de integração iniciarem.

A solução fechada é usar o fallback WASM oficialmente suportado pelo GoRules, sem lazy import e sem
inventar um binário ARM64 inexistente:

1. remover o override `@gorules/zen-engine-win32-x64-msvc` da aplicação;
2. configurar o `pnpm` versionado para instalar as arquiteturas `current` e `wasm32`;
3. regenerar o lockfile e provar, no host atual, que o import e a avaliação real do Zen Engine
   funcionam; e
4. deixar o gate `full` do Estaleiro verde.

## 3. Escopo de Arquivos

- **[UPDATE]** `apps/estaleiro/package.json` — remover integralmente o bloco
  `optionalDependencies` que só contém `@gorules/zen-engine-win32-x64-msvc`.
- **[UPDATE]** `pnpm-workspace.yaml` — acrescentar, no nível raiz, exatamente:

  ```yaml

  ```

  habilita somente o fallback portátil documentado pelo upstream.

  mudanças acima. Não atualizar versões alheias.

  anti-fake do motor: deve continuar executando um JDM real pelo import normal.

Não alterar `apps/estaleiro/core/src/workflow-composer.ts`, `packages/plugin-zen-engine/src/**`,
testes de EST-73, nem fazer lazy import: eles não são a causa e ampliariam o risco da correção.

## 4. Estratégia de Testes Estrita

1. Após a instalação, executar
   `pnpm --filter @plataforma/plugin-zen-engine test`; todos os testes existentes, incluindo
   `WorkflowEngine` que instancia `ZenEngine` e avalia fixtures JDM, devem passar. Isso falha se
   o módulo ainda não resolver no host ARM64.
2. Executar o smoke explícito no root, sem mock:

   ```bash
   pnpm --filter @plataforma/plugin-zen-engine exec node --input-type=module -e "import { ZenEngine } from '@gorules/zen-engine'; const engine = new ZenEngine(); console.log(engine instanceof ZenEngine)"
   ```

   Só é aceitável exit 0 e a impressão `true`; qualquer `MODULE_NOT_FOUND` bloqueia a task.
   A avaliação completa de JDM fica no cenário 1, que usa as fixtures já validadas
   em `tests/evaluate.test.ts`.
3. Executar `pnpm gate @plataforma/estaleiro --profile full` no host Windows ARM64; exige
   `allGreen=true`, incluindo os seis testes de integração que antes falhavam no load.
4. Antes de `finish`, verificar que a árvore está limpa e que o artefato `.gate/<tree>.json` tem
   `headSha` da branch C-36 e `allGreen=true`.

Fora de escopo: benchmark de desempenho WASM, suporte a outras plataformas e mudança do runtime
de produção para um pacote diferente.

### Pegadinhas conhecidas

- Não adicionar `@gorules/zen-engine-win32-arm64-msvc`: a matriz publicada pelo upstream não o
  oferece; a ausência é justamente a causa do incidente.
- Não manter o override x64 em paralelo com WASM: ele reintroduz uma arquitetura que não é a do
  host ARM64 e esconde a resolução desejada.
- Não considerar verde um gate da worktree EST-73 isolada: o único sinal de desbloqueio é o gate
  da C-36 e, depois, o candidato `master + EST-73`.
- `pnpm install` pode ser longo ou ter store inconsistente; aplicar os protocolos de P-001/P-003,
  nunca contornar a evidência com alteração manual do lockfile.
