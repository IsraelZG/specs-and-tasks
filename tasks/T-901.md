## 1. Objetivo
Construir um shell PWA instalável e offline-first em `apps/web` que **consome o `client-sdk`** (não a Bancada) para provar que o SDK é utilizável por um produto externo: login nos modelos 1 e 2 de identidade *(Modelo 3 — delegação de dispositivo — DESCOPADO desta v0, ver Seção 6)*, lista/edição local de um tipo de `CONTENT` colaborativo, e indicador de conectividade (peers conectados) *(derivado de `docs/plano-de-implementacao.md` §12 — "T-901 · PWA produto v0"; escopo de login e sincronização ajustado pela Decisão do Arquiteto de 2026-07-27, Seção 6)*.

**(2) Persister — `packages/client-sdk/src/persister.ts`** *(v0: grava direto em wa-sqlite na
main thread, SEM Worker — Decisão A-ii)*:

- Fábrica genérica real da TinyBase (assinatura verificada em
  `node_modules/tinybase/@types/persisters/index.d.ts`, pacote `tinybase@9.2.0` resolvido a partir
  de `^9.0.0`, módulo público `tinybase/persisters`):
  ```ts
  export function createCustomSqlitePersister<
    ListenerHandle,
    Persist extends Persists = Persists.StoreOnly,
  >(
    store: PersistedStore<Persist>,
    configOrStoreTableName: DatabasePersisterConfig | string | undefined,
    executeCommand: DatabaseExecuteCommand,
    addChangeListener: (listener: DatabaseChangeListener) => ListenerHandle,
    delChangeListener: (listenerHandle: ListenerHandle) => void,
    onSqlCommand: ((sql: string, params?: any[]) => void) | undefined,
    onIgnoredError: ((error: any) => void) | undefined,
    destroy: () => void,
    persist: Persist,
    thing: any,
    getThing?: string,
  ): Persister<Persist>;
  ```
- **A TinyBase não tem persister pronto para `wa-sqlite`.** Verificado por listagem de
  `node_modules/tinybase/persisters/`: só existem `persister-sqlite-wasm` (alvo
  `@sqlite.org/sqlite-wasm`, pacote **diferente** de `wa-sqlite`), `persister-sqlite3`,
  `persister-sqlite-bun`, `persister-cr-sqlite-wasm` — nenhum para `wa-sqlite`. O client-sdk
  precisa construir seu próprio wrapper com `createCustomSqlitePersister` acima.
- **API real do `wa-sqlite`** a usar dentro do wrapper — as mesmas chamadas já em produção, hoje,
  dentro de um Worker, em `packages/core/src/sqliteWasm.worker.ts:1-38`: `SQLiteESMFactory` de
  `wa-sqlite/dist/wa-sqlite-async.mjs`, `SQLite.Factory(module)`, `sqlite3.vfs_register(vfs, true)`,
  `sqlite3.open_v2(dbPath)`, `sqlite3.statements(db, sql)`, `sqlite3.bind_collection`,
  `sqlite3.column_names`, `sqlite3.step`, `sqlite3.row` — a portar para a **main thread** (v0 não
  usa Worker; sem protocolo `postMessage`).
- **⚠️ Risco técnico verificado nesta sessão (não é reabertura da Decisão A-ii, é uma correção de
  QUAL VFS usar dentro dela):** o VFS que `packages/core/src/sqliteWasm.worker.ts:1-4` usa hoje
  (`OriginPrivateFileSystemVFS`, de `wa-sqlite/src/examples/OriginPrivateFileSystemVFS.js:340`)
  chama `fileHandle.createSyncAccessHandle()`. Por spec da File System Access API, esse método só
  é permitido dentro de um dedicated Worker — lança fora dele. **Reusar esse VFS específico na main
  thread não é viável.** O mesmo pacote `wa-sqlite@1.0.0` (`^1.0.0`, já em
  `packages/core/package.json:18`) inclui VFS alternativos main-thread-safe, **verificados por grep
  sem nenhuma chamada a `createSyncAccessHandle`**: `IDBBatchAtomicVFS`
  (`wa-sqlite/src/examples/IDBBatchAtomicVFS.js`, backed por IndexedDB) e
  `IDBMinimalVFS`/`IDBVersionedVFS`. **O worker que implementar esta task deve registrar
  `IDBBatchAtomicVFS`** (`sqlite3.vfs_register(new IDBBatchAtomicVFS(dbName), true)`) **e não
  `OriginPrivateFileSystemVFS`.** Isso não contradiz a Decisão A-ii (continua wa-sqlite, continua
  main thread, continua sem Worker) — só fixa qual VFS do pacote é tecnicamente compatível com ela.

```ts
// packages/client-sdk/src/persister.ts
export function createWaSqlitePersister(
  store: ClientStore,
  dbName: string,
): Promise<Persister<Persists.StoreOnly>>; // Persister/Persists — tinybase/persisters
```
