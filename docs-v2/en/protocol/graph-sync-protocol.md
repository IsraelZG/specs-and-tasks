# Graph Sync Protocol — authoritative change feed

This document defines the synchronization protocol of the official graph.
It replaces RBSR as the normal path. RBSR remains a helper audit algorithm
between authority replicas.

## 1. Model

The authority maintains a change feed per authorized partition. The feed is
an append-only sequence of official records. Each partition has a monotonic
cursor.

The authority groups records into batches. Each batch has a signed manifest.
The manifest proves batch order and completeness. Peers can deliver the
record bytes. Only the manifest proves position in the feed.

## 2. Exact types

All identifiers are 26-character ULIDs in Crockford Base32. All hashes are
32-byte SHA-256. All signatures are 64-byte Ed25519. The transport encoding
is MessagePack. In persistence and logs, hashes and keys use lowercase hex.

```typescript
type Ulid = string;          // 26 chars, Crockford Base32
type Hash32 = Uint8Array;    // 32 bytes, SHA-256
type PubKey = Uint8Array;    // 32 bytes, Ed25519 public
type Signature = Uint8Array; // 64 bytes, Ed25519

// Monotonic cursor of a partition. Starts at 0. Increments by 1.
type Cursor = bigint;        // uint64, no gaps in the partition

interface PartitionId {
  network_id: Ulid;
  partition: string;         // partition slug, max 64 chars
}

interface FeedRecord {
  network_id: Ulid;
  partition: string;
  cursor: Cursor;            // position in the partition feed
  record_id: Ulid;           // id of the graph node or edge
  record_hash: Hash32;       // SHA-256 of the canonical record envelope
  record_kind: 'node' | 'edge' | 'compensating_event';
  author_key: PubKey;        // key of the confirmed proposal author
  authority_epoch: number;   // epoch of the confirming authority
  confirmed_at: number;      // ms Unix, authority clock
}

interface BatchManifest {
  version: 1;
  network_id: Ulid;
  partition: string;
  cursor_start: Cursor;      // cursor of the first batch record
  cursor_end: Cursor;        // cursor of the last batch record
  prev_manifest_hash: Hash32;  // hash of the previous partition manifest
  record_ids: Ulid[];        // ids in feed order
  record_hashes: Hash32[];   // hashes in the same order as record_ids
  authority_epoch: number;
  issued_at: number;         // ms Unix
  authority_key: PubKey;
  signature: Signature;      // signs the canonical serialization above
}

interface Proposal {
  proposal_id: Ulid;         // idempotency: generated by the client
  network_id: Ulid;
  partition: string;
  author_key: PubKey;
  ucan: Uint8Array;          // serialized authorization token
  payload: Uint8Array;       // serialized domain operation
  created_at: number;        // ms Unix, client clock
  signature: Signature;      // signs all fields above
}

type ProposalResult =
  | { status: 'confirmed'; cursor: Cursor; record_hash: Hash32 }
  | { status: 'rejected'; error: SyncError };
```

## 3. Limits and encoding

| Item | Limit |
| :--- | :--- |
| Records per batch | maximum 1,024 |
| `record_ids.length` | equal to `record_hashes.length` |
| Batch interval | `cursor_end - cursor_start + 1 == record_ids.length` |
| Proposal payload | maximum 256 KiB |
| Transport frame size | maximum 1 MiB before parse |
| Protocol version | `1`. Higher versions go to quarantine |

The cursors of a partition have no gaps. The authority rejects a batch with an invalid interval
or diverging counts before any write.

## 4. Read flow

1. The client authenticates the authority through the wire protocol
   handshake.
2. The client sends its last applied cursor per partition.
3. The authority sends the next authorized manifest.
4. The client chooses a source for each batch record.
5. The source can be the authority or an authorized peer.
6. The client validates the hash of each record against
   `record_hashes`.
7. The client validates the signature and permission of each record.
8. The client validates the manifest signature and the
   `prev_manifest_hash` chain.
9. The client writes the whole batch in a single local transaction.
10. The client advances the local cursor after commit.
11. The client asks the authority for any record gap.

A peer can deliver bytes. The client treats peer bytes as untrusted until
the validation in steps 6 to 8.

## 5. Write flow

1. The client writes each proposal offline to a durable local outbox.
2. A proposal in the outbox does not belong to the official graph.
3. The client sends the proposal when it regains the connection.
4. The authority validates identity, powers, permission and domain rules.
5. The authority rejects or confirms the proposal.
6. The confirmation creates an official record in the change feed.
7. The client marks the proposal confirmed when it observes its
   `record_hash` in the feed.

The authority answers every proposal with `ProposalResult`. The client
retries after timeout. The `proposal_id` guarantees idempotency. A repeated
proposal returns the same result without creating a second record.

## 6. Corrections

No correction changes a confirmed record. Every correction creates a
compensating event. The compensating event is a `FeedRecord` with
`record_kind = 'compensating_event'`. It references the corrected record in
the payload. The original record remains in the feed.

## 7. Operation without the authority

During a temporary authority failure:

1. The client reads its local cache.
2. The client edits local documents and creates outbox proposals.
3. Peers exchange records covered by already known manifests.
4. Peers do not advance the official finality of the graph.
5. The client shows in the interface that the data may be stale.

Local commutative operations continue. Non-commutative operations wait for
the authority. The affected scope degrades to read-only without integrity
loss.

## 8. Normative errors

| Code | Condition | Client action |
| :--- | :--- | :--- |
| `STALE_EPOCH` | `authority_epoch` diverges | synchronize identity before continuing |
| `CURSOR_GAP` | `cursor_start` is higher than expected | ask the authority for gaps |
| `MANIFEST_SIGNATURE_INVALID` | manifest signature failed | discard the batch and report |
| `RECORD_HASH_MISMATCH` | record hash diverges from manifest | discard the record and change source |
| `PROPOSAL_REJECTED` | domain rule or permission failed | remove from outbox and log the reason |
| `PERMISSION_DENIED` | UCAN invalid or insufficient | renew credential with the authority |
| `QUARANTINE` | unknown version or format | preserve bytes outside projections |

## 9. Persistence and transaction

The client applies a batch in a single SQLite transaction. The transaction
writes the records, the manifest and the new cursor. If any validation
fails, the transaction aborts in full. The local cursor never advances
without commit.

## 10. Idempotency

- Receiving the same batch twice does not change state. The client compares
  the manifest hash with the local cursor.
- Sending the same proposal twice returns the same `ProposalResult`.
- Reapplying an already present record is a deterministic no-op.

## 11. Compatibility

- Unknown fields in MessagePack maps stay preserved and ignored.
- The signed record envelope is invariant across frame versions.
- A manifest with `version` higher than supported goes to quarantine.

## 12. Conformance tests

1. Two clients with the same initial cursor converge to the same state
   after the same batch.
2. A batch delivered by a hostile peer with one altered byte fails in step
   6.
3. The authority rejects a manifest with an incorrect `prev_manifest_hash`.
4. A proposal sent twice creates a single feed record.
5. An authority failure during a write confirms no partial proposal.
6. A compensating event does not change the original record.
7. The local cursor never passes the last validated manifest.
